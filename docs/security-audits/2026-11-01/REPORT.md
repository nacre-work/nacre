## 1. Posture summary

Across 19 coverage-led hunter assignments spanning authentication, OAuth/delegation, the REST and MCP surfaces, ingest, the resolver/RLS boundary, sidecars, deployment configuration, and supply chain, this run confirmed 19 findings (2 high, 6 medium, 11 low) and left 9 as needs_validation (source-grounded hypotheses blocked on something outside the sandbox — an external identity provider, a real embedder, deployment-specific nginx or proxy configuration, or similar). ### Finding write-ups

### Published example JWT secret accepted at startup, including in production

<a id="packages-core-config-ts-loadjwtkeys-published-example-secret-accepted"></a>**Severity: HIGH** (likelihood medium, impact critical) · confidence high · fingerprint `packages/core/config.ts:loadJwtKeys:published-example-secret-accepted`

`.env.example` ships `NACRE_JWT_SECRET=development-only-not-a-secret-0123456789` (line 154). `loadJwtKeys` (packages/core/config.ts:726) validates only that the secret is >=32 bytes; it never compares the value against the published default, and no other startup check (including the `NACRE_ENV === 'production'` checks at config.ts:1365-1372) looks at the secret's value either. `docs/quickstart.md`'s documented 'First run' path (the path meant to lead to a real deployment, as opposed to the explicitly-ephemeral 'Two minutes' demo path a few lines above it) runs `cp .env.example .env` (quickstart.md:105) and never instructs the reader to regenerate `NACRE_JWT_SECRET` before going further. Anyone who has read the public repository therefore knows a value that, if still configured, lets them forge a JWT with an attacker-chosen `org`, `principal_type` and `role` (including `org_admin`) that the API's `authenticate()` accepts, because the role is taken directly from the verified claims (auth.ts:564) with no further check against a real session, user row, or grant.

**Root cause.** loadJwtKeys (packages/core/config.ts:726) checks only `secret.length < 32`, never the secret's value, and loadConfig's production-only checks (config.ts:1365-1372) check `canonicalUrl` and never the JWT secret. Nothing in the startup path refuses a token-signing secret that is known/public.

**Reproduction.** All 4 tests passed (agents/v25/artifacts/result.txt): loadConfig accepted the published secret under NACRE_ENV=production without throwing; loadJwtKeys returned a usable HS256 key from the published secret; a JWT forged with that secret and role='org_admin'/org='attacker-org' verified successfully against the exact key material and algorithm authenticate() uses, yielding payload.role==='org_admin' and payload.org==='attacker-org'. This independently reproduces the hunter's claimed result without relying on their artifact.

**Fix.** In loadJwtKeys and loadJwtVerification, refuse a small set of known-published secret values (at minimum the exact .env.example value) outright, with a message naming the variable and pointing at `openssl rand -base64 32`. Ship .env.example with NACRE_JWT_SECRET empty (as the embedding endpoint already is) rather than populated, and have the quickstart's 'First run' path generate one explicitly, the way the 'Two minutes' demo path already explains why its copy is acceptable there.


### Skill zip import repeats synchronous inflate over overlapping compressed entries, before authorization

<a id="packages-core-skill-ts-readskillzip-overlapping-compressed-input-before-authz"></a>**Severity: HIGH** (likelihood medium, impact high) · confidence high · fingerprint `packages/core/skill.ts:readSkillZip:overlapping-compressed-input-before-authz`

readSkillZip (packages/core/skill.ts) bounds each entry's declared uncompressed size against SKILL_LIMITS.fileBytes and the running sum of declared sizes against SKILL_LIMITS.totalBytes, but it never bounds, sums, or checks for overlap in the *compressed* byte range (`localOffset`..`localOffset+compressed`) that it hands to `inflateRawSync`. A central-directory entry can declare size=0/crc=0 (contributing nothing to the declared-size budget) while its `compressed` field spans up to the whole request body, and up to `SKILL_LIMITS.files*4` (256) such entries can all point at one shared compressed region. Each is inflated independently and synchronously, so total CPU work scales with (entry count) x (shared blob size) while the uploaded body only grows by the ~50-byte central-directory record per entry. On REST, `PUT /v1/skills/layers/{any-uuid}` with `Content-Type: application/zip` reads a body up to NACRE_MAX_DOCUMENT_BYTES (50 MiB default) and calls readSkillZip (server.ts:1745) before `skills.write`'s `gate()` (skills.ts:550) checks whether the layer exists, is visible, or is writable by the caller — so any authenticated principal, including a member with zero grants or a service account that cannot see the target layer, can trigger the full cost before being refused. MCP's `update_skill` (services.ts:634) has the identical ordering, bounded by the MCP transport's 1 MiB body cap (server.ts:203/266) rather than NACRE_MAX_DOCUMENT_BYTES.

**Root cause.** readSkillZip accounts only declared (post-inflate) sizes; `compressed` is read from the central directory (skill.ts:310) and used only to slice the archive buffer for `inflateRawSync` (skill.ts:328-330,339), never bounded relative to the declared size and never checked against other entries for the same local-data range. `inflateRawSync`'s `maxOutputLength: size + 1` option only aborts on excess *output*, so a compressed region that is cheap to construct (e.g. a run of empty DEFLATE "stored" blocks) but decodes to 0 or few bytes is processed in full every time an entry references it, and nothing rejects two or more central-directory entries whose local-data ranges coincide. Both call sites that invoke readSkillZip (server.ts:1745 for REST, services.ts:634 for MCP) run before the handler resolves the target level and calls `skills.write`, whose private `gate()` (skills.ts:550) is the only place visibility and write-permission are checked.

**Reproduction.** readSkillZip never refuses overlapping compressed ranges: with a single shared 1,000,000-byte compressed region, 1 referencing central-directory entry took ~3.06 ms and 256 referencing entries (the code's own cap, SKILL_LIMITS.files*4) took ~394.86 ms — a ~129x increase in CPU time for only ~13.6 KB of added request body (central-directory records), while the request body already legitimately needed to carry the 1 MiB shared region once. A separate run over a 2 MiB shared region showed the same scaling (1->64 entries: ~3.97 ms -> ~161.20 ms, a ~40.6x increase). A standalone zlib timing (without the skill-archive wrapper) confirmed the underlying mechanism scales close to linearly with the shared blob's byte length (1 MiB: ~2.23 ms, 5 MiB: ~5.82 ms, 10 MiB: ~11.38 ms, 20 MiB: ~23.76 ms), so extrapolating to NACRE_MAX_DOCUMENT_BYTES's REST default (~50 MiB) and the code's 256-entry cap gives a projected single-request cost on the order of several seconds to ~15-20 seconds of fully synchronous CPU inside the API process -- all of it incurred by readSkillZip before skills.write's gate() has checked whether the caller may write (or even see) the targeted layer. Raw transcripts: agents/v27/artifacts/result.txt, agents/v27/artifacts/result2.txt, agents/v27/artifacts/result3.txt.

**Fix.** Bound the compressed work the same way the uncompressed work is bounded, and move the parse after authorization. (1) In readSkillZip, sum each entry's `compressed` length into the same (or a parallel) running total and refuse once it exceeds a fixed multiple of SKILL_LIMITS.totalBytes, independent of declared `size`; this closes the near-zero-declared-size loophole regardless of overlap. (2) Reject central-directory entries whose local-data byte range (`localOffset`..`localOffset+compressed`) overlaps a previously-accepted entry's range, since a well-formed archive never needs two entries to share local data. (3) In both server.ts's handleSkills and services.ts's update_skill, resolve the target level and run skills.write's gate()-equivalent visibility/permission check before calling readSkillZip, so a caller who may not write (or see) the level is refused before any parsing cost is spent.


### A member can approve an OAuth connection that acts as any service account in the organization

<a id="api-oauth-consent-agent-visibility-via-unfiltered-service-account-list"></a>**Severity: MEDIUM** (likelihood low, impact high) · confidence high · fingerprint `api/oauth-consent/agent-visibility-via-unfiltered-service-account-list`

In the agent flow of POST /v1/oauth/consent, the request body names a service_account_id, and nothing on that path checks the caller's role. The handler is meant to accept only an agent 'this caller can see'. It checks that by looking for the id in options.serviceAccounts.list(auth). PostgresServiceAccounts.list filters only on org_id, so a plain member gets back every service account in the organization and the visibility check always passes. Everywhere else, listing and minting service accounts is org_admin only, and docs/authz.md says the agent flow is an org_admin act. Yet a member can register a client through open RFC 7591 registration, post consent with their own console session naming any service account's uuid, and get back an authorization code. Exchanging the code at /oauth/token gives an access token and refresh token that act as that service account, so the member reaches that account's grants instead of their own.

**Root cause.** The agent branch of the consent handler bases its authorization decision on a visibility check that calls PostgresServiceAccounts.list. That method returns every service account in the organization whatever the caller's role. There is no administers(auth) gate on the non-administrative agent path; the only administers() check in the handler sits inside the administrative-MCP branch.

**Reproduction.** The promoted hunter artifact (agents/h01-delegation/artifacts/result.txt) records a test against a real PostgreSQL through the shipped createApi handler: 'UNIT2 member-as-agent-consent status=200 hasCode=true body={"redirect_to":"http://127.0.0.1:33419/callback?code=nacre_ac_..."}'. A member received an authorization code for a connection acting as a service account they do not administer. This verifier re-checked every line of the path in source and found no preventing layer. The verifier's own re-run was not completed, so no v01 artifact is cited.

**Fix.** In the agent branch (service_account_id present), require administers(auth) before the visibility loop and answer 404 otherwise, matching the gate on GET/POST /v1/service-accounts. Alternatively, give the visibility check a lookup scoped to the caller's role instead of reusing PostgresServiceAccounts.list. Add an authz case asserting that a member naming an existing service account gets 404 and that no consent row is stored.


### An OAuth connection acting as a service account keeps renewing after the service account is revoked

<a id="api-oauth-refresh-service-account-revocation-not-rechecked"></a>**Severity: MEDIUM** (likelihood medium, impact medium) · confidence high · fingerprint `api/oauth-refresh/service-account-revocation-not-rechecked`

PostgresOAuthRefreshTokens.rotate (packages/api/src/oauth-store.ts) re-checks revocation of the acting principal only for a delegation (acts_as='user'): its SELECT computes `suspended` from a LEFT JOIN on `users` gated by `c.acts_as = 'user'` (oauth-store.ts:827-829), and separately refuses when `c.revoked_at IS NOT NULL` on the connection itself. Neither clause ever reads `service_accounts.revoked_at`. For a connection whose subject is a service account (acts_as='service_account'), rotate() falls straight through to returning a MintRequest (oauth-store.ts:879-882), and the token endpoint (server.ts:4007-4080) mints a fresh service-account access token and reissues the refresh token. The minted JWT has `principal_type:'service_account'` and no `del` claim (oauth-mint.ts: `del` is only added when `delegated`, i.e. actsAs==='user'); authenticate() treats the absence of `del` as 'not a delegation' and returns `base` immediately with no table lookup at all (auth.ts:591-595). effectivePrincipals (packages/core/authz/principals.ts) and loadGrants (packages/core/authz/store.ts) resolve purely from the principal ref and never consult service_accounts.revoked_at either. So once an administrator revokes a service account via DELETE /v1/service-accounts/{id} (-> PostgresServiceAccounts.revoke, server.ts:6790-6799), the account's own nacre_sk_ key stops working immediately (service-keys.ts:91-96 filters revoked_at IS NULL on every lookup), but any OAuth connection that was approved to act as that service account keeps minting valid, fully-privileged access tokens for that account indefinitely, because every refresh re-extends the family with no revocation check at all.

**Root cause.** PostgresOAuthRefreshTokens.rotate's revocation re-check is written only for the delegated case (c.acts_as = 'user'); it has no equivalent LEFT JOIN against service_accounts for acts_as = 'service_account', so renewing a service-account connection never consults the one column (service_accounts.revoked_at) that is supposed to end that account's authority. Downstream, authenticate() verifies a service-account JWT by signature alone (no `del` claim means an immediate `return base`), and the resolver (effectivePrincipals/loadGrants) never re-checks a service account's revocation state either, so nothing after rotate() can catch what it missed.

**Reproduction.** revoked_at was set on the service account (revoke() returned true, confirmed by a direct SELECT), yet rotate() returned a full MintRequest -- {orgId, consentId, family, subject:{actsAs:'service_account', serviceAccountId}} -- rather than undefined or 'suspended'; server.ts would mint a fresh service-account access token and reissue a refresh token from this, exactly as before the revocation. Reproduced independently against a real PostgreSQL (agents/v32/artifacts/result.txt), consistent with h01-delegation's own result2.txt.

**Fix.** In PostgresOAuthRefreshTokens.rotate, extend the single SELECT with a LEFT JOIN against service_accounts (by c.service_account_id and org_id) and fold (c.acts_as = 'service_account' AND sa.revoked_at IS NOT NULL) into the refusal -- most naturally into the existing `revoked` check (treat it as equivalent to the connection's own revoked_at, since a revoked service account's authority should end exactly like a revoked connection's) rather than into `suspended` (revoking an account, unlike disabling a person, is not something the product currently reverses). As defence in depth, since an already-minted access token is still accepted purely by signature for its remaining TTL, the resolver/authenticate path could additionally treat a service_account principal whose row is revoked as unauthorized -- mirroring stillActing's existing active() re-check, which today only runs for upload-ticket redemption and never for an ordinary bearer-token request.


### Open OAuth client registration validates an unbounded redirect_uris list with an O(n^2) membership check, allowing cheap single-request CPU exhaustion

<a id="packages-api-src-server-ts-oauth-register-unbounded-redirect-uris"></a>**Severity: MEDIUM** (likelihood high, impact medium) · confidence high · fingerprint `packages/api/src/server.ts:oauth-register:unbounded-redirect-uris`

POST /oauth/register (server.ts:3850) is reached before authenticate() (server.ts:4183) is ever called and is gated only by the generic per-source client_registration budget (100/hour by default). The handler reads redirect_uris into an array with no count or length bound (server.ts:3864-3869) and validates it with `uris.every(u => redirectAllowed(u, uris))` (server.ts:3880); redirectAllowed delegates to exactRedirect, whose check is `registered.includes(uri)` (authserver.ts:201) - an O(n) linear scan performed once per URI, making the whole validation O(n^2) in the length of the attacker-supplied list. The only other bound is the generic 1,000,000-byte body cap (server.ts:1202), so a single request can carry roughly 25,000-26,000 short https URIs. I reproduced the cost directly: importing the exact exported `redirectAllowed` function the handler calls and timing `uris.every(...)` over synthetic https URIs inside the sandbox showed clearly superlinear growth (1,000 URIs: 18.6ms; 4,000: 205ms; 16,000: 2,172ms), and a single payload built to sit just under the 1,000,000-byte body limit (25,800 URIs, 995,127 bytes) took 3,897ms of synchronous, single-threaded computation to validate - before any authentication and before the row is even written. The sibling door for the same table, validateMetadataDocument (client-metadata.ts:106), caps the equivalent list at 20 entries of at most 512 characters and is the comparable baseline that shows this is an omission rather than this codebase's general pattern. Persisted rows are swept by the worker only after UNAPPROVED_CLIENT_DAYS = 7 days unseen with no consent and no authorization (adapters.ts:885,902-919), and the authorize endpoint's touch() (oauth-store.ts:350-357) resets last_seen_at on every call, so a client that is merely walked through /oauth/authorize stays out of that sweep indefinitely.

**Root cause.** The registration handler omits the per-field bound (entry count and per-string length) that validateMetadataDocument already applies to the same table's other entry door, and redirectAllowed/exactRedirect reuse a plain-array membership scan (`registered.includes(uri)`) that is O(n) per call; calling it once per URI inside `uris.every(...)` makes the self-asserted redirect_uris array's validation cost O(n^2) in its length, with no upper bound on that length besides the generic 1,000,000-byte body cap.

**Reproduction.** Validation time grows far faster than the input: N=1000 -> 18.6ms, N=4000 (4x) -> 205.5ms (~11x), N=16000 (16x) -> 2172.2ms (~117x from the N=1000 baseline), consistent with the O(n^2) cost that `registered.includes(uri)` inside `every()` implies. At the realistic worst case for a single request - 25,800 URIs serialized to 995,127 bytes, just under the handler's own 1,000,000-byte body cap - the identical check took 3,897ms of synchronous computation. This single call is what POST /oauth/register executes on the shared Node.js event loop, unauthenticated, before any client row is written, for every request the per-source budget admits (100/hour by default).

**Fix.** Bound redirect_uris on POST /oauth/register the same way validateMetadataDocument already bounds it for the identical column on the CIMD door - refuse more than a small fixed count of entries (e.g. 20) or any entry over a fixed length (e.g. 512 characters) before running any per-URI check - and make the per-URI check itself O(1) regardless of list size, e.g. by building a Set of the registered URIs once per validation call instead of calling Array.prototype.includes once per entry inside exactRedirect.


### Per-client sign-in limit becomes a single global bucket behind the shipped nginx front door

<a id="packages-api-src-source-ts-clientsource-trust-proxy-default-behind-shipped-front-door"></a>**Severity: MEDIUM** (likelihood high, impact medium) · confidence high · fingerprint `packages/api/src/source.ts:clientSource:trust-proxy-default-behind-shipped-front-door`

NACRE_TRUST_PROXY defaults to 0 in every shipped topology (Compose's .env.example, every Compose profile, and the Helm chart's values.yaml), while every shipped topology also runs nginx (docker/nginx.conf.template, service `web`, present in every Compose profile with no `profiles:` restriction) in front of the API and proxies all of `/v1/`, `/oauth/` and `/.well-known/` to it. At trustProxy=0, clientSource() unconditionally ignores X-Forwarded-For and returns req.socket.remoteAddress, which for every proxied request is nginx's own address. ### An ingest racing a layer delete commits a live document into the deleted layer; the worker claims it and the collector never reclaims it

When object storage is configured it then PUTs the bytes, and only after that does it upsert the document row. It tombstones the layer's points, sets deleted_at on the rows its UPDATE can see, marks the layer deleted and commits. No row lock is shared between the two transactions, and the ingest never checks the layer again.

If the delete commits inside that window, the upsert has one of two outcomes:
- For a new external_id, it inserts the row live (status pending, deleted_at NULL).
- For an existing external_id, it resurrects the row the delete just tombstoned, under the same id, through deleted_at = NULL and the REQUEUE predicate.

- The worker's claimNext joins layers with no liveness predicate, so it claims the document and would index it with deleted:false points.
- The collector claims only rows with deleted_at set, so the chunk text, points and stored object stay forever.
- The layer cannot be deleted a second time, because remove returns false.
- PostgresDocuments.read, which also omits l.deleted_at, still returns the document to a role-based 'all' reader such as org_admin.
- Search hydration (HYDRATE_SQL) drops those hits, but only after they have taken top_k slots.

The effect is that a lower-trust writer's document survives an administrator's deletion of the layer, and the deletion is silently incomplete.

**Root cause.** A check-then-act race on the layer's lifecycle. writableLayer (adapters.ts:1232) checks the layer without a lock, and PostgresLayers.remove (adapters.ts:2002-2044) takes no lock that an ingest also takes. The upsert (adapters.ts:1359, deleted_at = NULL at 1440, REQUEUE at 155-158) can therefore commit into a layer that was deleted after the check. The lifecycle predicates downstream also disagree: the worker claim (claim.ts:76) and PostgresDocuments.read (adapters.ts:228) join layers without l.deleted_at IS NULL, while HYDRATE_SQL (adapters.ts:118-119) requires it.

The hunter's artifact independently shows the existing-document variant, where the row was resurrected under the same id.

In-flight ingests then finish first and the delete's UPDATE tombstones them, and a later ingest re-evaluates deleted_at under its lock and is refused. As defence in depth, add l.deleted_at IS NULL to the worker claim, to PostgresDocuments.read, and to the retry, updateMetadata and remove lookups. **Root cause.** PostgresWorkspaces.list resolves the person's read plan (adapters.ts:2473). **Reproduction.** For both persons, authenticate() produced delegation.layers = [hb] and PostgresLayers.list returned ["hb"]. ### Layer document_count and failed_count include documents denied to the caller

<a id="packages-api-src-adapters-ts-layer-document-count-includes-denied-documents"></a>**Severity: LOW** (likelihood low, impact low) · confidence high · fingerprint `packages/api/src/adapters.ts:layer-document-count-includes-denied-documents`

### POST /v1/me/password with Idempotency-Key stores the enrolment challenge in plaintext in the idempotency cache for 24 hours

<a id="packages-api-src-idempotency-ts-credential-fields-enrolment-challenge"></a>**Severity: LOW** (likelihood low, impact medium) · confidence high · fingerprint `packages/api/src/idempotency.ts:CREDENTIAL_FIELDS:enrolment-challenge`

A sign-in gate can answer 'enrol' on the password-change path. When it does, POST /v1/me/password responds 200 with {second_factor_enrolment_required, challenge, expires_in: 900, reason}. The challenge is a bearer JWT: audience <aud>/second-factor, purpose 'enrol', valid for 900 s. It is stateless, so it can be used more than once until it expires. readEnrolmentChallenge accepts it at the narrow enrolment door (/v1/me/second-factor*), where its holder can add a TOTP or WebAuthn factor to the named account and then receive a full session through onEnrolled/sessionAfterEnrolment. If the request carried an Idempotency-Key, the decorated res.end hands the parsed body to Idempotency.store. carriesCredential does not know the field name 'challenge', so the body is written to Redis with EX 86400 and replayed on repeats. idempotency.ts has its own rule that a response carrying a credential is never cached, because Redis has no access control of its own; this response breaks that rule.

**Root cause.** Credential detection uses a field-name list, CREDENTIAL_FIELDS (idempotency.ts:94), and the list omits 'challenge'. The route-based fallback NEVER_CACHED (server.ts:2128) does not cover /v1/me, so nothing else keeps the enrolment-challenge body sendSessionOutcome writes (server.ts:2584-2589) out of the cache.

**Reproduction.** The control stored 0 keys. carriesCredential(enrolment body) returned false. The enrol request answered 200 with keys [second_factor_enrolment_required, challenge, expires_in, reason]. Redis then held exactly one key, nacre:idem:22222222-…:user:dddddddd-…:eejqVhpG…, with ttl 86400, whose stored challenge equals the one in the response. The real Login.readEnrolmentChallenge accepted the challenge read from Redis and returned {orgId: 22222222-…, userId: dddddddd-…}, which is the identity the enrolment door acts on. The repeat request returned 200 with idempotency-replayed: true. The verifier did not drive the full enrolment ceremony; the exchange for a factor and a session is source-visible at server.ts:4238-4287 and login.ts:509-513.

**Fix.** Treat any challenge as a credential. Add 'challenge' to CREDENTIAL_FIELDS. WebAuthn begin options also carry a challenge, so those responses become uncached too, which only costs a replay. As defence in depth, add /v1/me to NEVER_CACHED, since every answer there concerns the caller's own credentials. Extend idempotency-secrets.test.ts to assert that carriesCredential is true for the enrolment-outcome body sendSessionOutcome writes, rather than collecting only fields the contract describes as returned once.


### Concurrent demote/disable changes race past the last-administrator guard and can leave an organization with no org_admin

<a id="packages-api-src-principals-ts-postgresusers-update-last-admin-count-write-skew"></a>**Severity: LOW** (likelihood low, impact low) · confidence high · fingerprint `packages/api/src/principals.ts:PostgresUsers.update:last-admin-count-write-skew`

PostgresUsers.update refuses a change that would leave an organization with no active org_admin. It does this by locking the target user's row FOR UPDATE and then counting the other active org_admins with an unlocked SELECT, inside withOrg's plain BEGIN, which runs at READ COMMITTED. Suppose two transactions each demote or disable a different administrator. They lock different rows, so neither waits for the other. Each counts the other administrator as still active, because the other transaction's UPDATE has not committed yet. Both pass the guard and both commit. Three doors reach this one call: PATCH /v1/users/{id}, DELETE /v1/users/{id} (which disables), and the administrative-MCP set_person_role/disable_person apply. Through any of them, two administrators acting at the same time, or one administrator sending 'disable the other' and 'disable me' together, can leave the organization with zero active org_admins. The handler's own comment says no core API route can recover from that.

**Root cause.** onTargetUser takes FOR UPDATE only on the target row (principals.ts:406). The guard then counts the other active administrators with a plain SELECT (principals.ts:439-442) inside withOrg's default READ COMMITTED transaction (core/db/client.ts:156). The invariant 'at least one active org_admin' covers a set of rows, so locking one row per transaction cannot serialize two writers that target different administrators. This is classic write skew. The comment at principals.ts:433-436 claims the combination stops mutual concurrent demotion, but that holds only when both transactions target the same row.

**Reproduction.** Sequential control: first=updated, second=last-admin, 1 active org_admin. Barrier mutual demotion: a_demotes_b=updated, b_demotes_a=updated, 0 active. Barrier disable-other plus self: both updated, 0 active. Unsynchronised: 17 of 20 runs ended with 0 active org_admins. Recorded in agents/v19/artifacts/result.txt; the hunter's own run is in agents/h05-admin/artifacts/result.txt.

**Fix.** Serialize every role or disable change within an organization before the guard reads anything. Take a transaction-scoped advisory lock keyed by the organization at the start of onTargetUser (the repository already uses pg_advisory_xact_lock(hashtextextended(...)) in notifications.ts and login.ts). Alternatively, lock every active org_admin row FOR UPDATE, in a fixed order, before counting. Add a concurrency regression test that runs mutual demotion and disable-other-plus-self in parallel and asserts one 'last-admin' result and one remaining active org_admin.


### Consent approves and delivers an authorization code to a redirect URI that a metadata-document client has dropped, after authorize stops accepting it

<a id="packages-api-src-server-ts-oauth-consent-metadata-client-cache-freshness"></a>**Severity: LOW** (likelihood low, impact medium) · confidence high · fingerprint `packages/api/src/server.ts:oauth-consent:metadata-client-cache-freshness`

A client can be identified by its Client ID Metadata Document. For such a client, GET /oauth/authorize uses the cached oauth_clients row only while refresh_after is in the future. Once the row is stale, authorize refetches the document, and a failed fetch is a refusal (resolveMetadataClient). The stated purpose is that a client which dropped a redirect URI stops receiving codes there.

POST /v1/oauth/consent re-reads the same row with the raw oauth.clients.find and checks it with clientRedirectAllowed, with no freshness rule. This applies to both Approve (server.ts:6538-6539) and Cancel (6395-6396). The console consent screen takes client_id, redirect_uri and code_challenge straight from the URL fragment (consent.ts readRequest), so nothing requires the browser to have passed through /oauth/authorize. A stale row is rewritten only by a successful refetch, which happens on an authorize call. A failed refresh leaves the old redirect_uris in place. Rows with a consent or authorization are never swept, and unapproved ones are swept only after 7 days unseen.

The result: someone who controls a redirect URI the client's current document no longer lists can craft a link `#/consent?client_id=<document URL>&redirect_uri=<dropped URI>&code_challenge=<their own S256 challenge>`. If a signed-in person approves it, the server mints a code bound to the dropped URI and returns redirect_to with the code. The token endpoint does not re-check the client: it compares the code_verifier, and client_id and redirect_uri only when they are supplied. So the link's author exchanges the code for an access token and a refresh token acting as that person. The screen names the legitimate client's document URL, not the attacker.

**Root cause.** The freshness rule for metadata-document clients is enforced only inside resolveMetadataClient, which only GET /oauth/authorize calls. The consent handler is where a code or a refusal is actually delivered, and both its decisions call the raw store lookup PostgresOAuthClients.find, which returns the row whatever refresh_after says. So the two points apply different redirect-URI policies to the same client, even though clientRedirectAllowed's own comment says they must ask the same question.

**Reproduction.** Authorize refused the stale client (400 invalid_client), while consent answered 200 with redirect_to=https://old.example/cb?code=nacre_ac_..., and the token endpoint exchanged that code for an access token and a refresh token (200). After a successful refetch the same consent request answered 400 'Unknown client, or a redirect_uri it did not register.' So the stale row is the cause.

**Fix.** Resolve the client through one function at all three delivery points. Factor out a freshness-enforcing lookup: for a client whose source is 'metadata', return the row only while refreshAfter > now, and otherwise refetch through the egress guard, refusing on failure. Call it from GET /oauth/authorize and from both consent decisions instead of oauth.clients.find. Optionally, also have the token endpoint refuse a code whose metadata client's current redirect_uris no longer admit approved.redirectUri. Add a live case: a stale row plus a document that dropped the URI must make consent Approve and Cancel answer 400.


### A restricted OAuth delegation can list and end every other connection its person approved

<a id="packages-api-src-server-ts-oauth-consents-list-and-revoke-accept-delegated-token"></a>**Severity: LOW** (likelihood low, impact medium) · confidence high · fingerprint `packages/api/src/server.ts:oauth-consents-list-and-revoke-accept-delegated-token`

GET /v1/oauth/consents and DELETE /v1/oauth/consents/{id} authenticate a delegated access token like any other and never test auth.delegation. A connected application that a person limited to {read} on one layer L can therefore call these two routes with its own token and reach every connection that same person approved: it can enumerate them (client name, ceiling permissions, narrowing layer ids, approver email, surface) and revoke any of them -- including a {read,write} connection narrowed to a different layer M, and, when the person is an org_admin, their administrative MCP connection (surface=admin), which also cancels that connection's open proposals. **Root cause.** server.ts's GET /v1/oauth/consents (line 6257) and DELETE /v1/oauth/consents/{id} (line 6315) hand the AuthContext straight to PostgresOAuthConsents.list/revoke with no auth.delegation check. Those store methods scope a non-administering caller by `approved_by = auth.principal.id` only (oauth-store.ts lines 617 and 690). For a delegated token, auth.principal.id is set to delegation.userId -- the person, not the connection (auth.ts, the branch after `if (claims.del === undefined)` returns `principal: { type: 'user', id: delegation.userId }`). administers(auth) (auth.ts:220) is false for any delegation that is narrowed (`auth.delegation?.layers !== undefined`) or lacks the 'admin' ceiling value, so such a token takes the `mine` branch and that branch matches every row the person approved, not only the row the token's own `del` claim names.

**Reproduction.** POST /v1/oauth/consent -> 404 (control, confirms the T41 refusal fires for this same token). DELETE of that pipeline connection with the same {read}/L token -> 200 {ended:true}; revoked_at set, 0 refresh tokens remained, and the pipeline's delegation (PostgresDelegations.resolve) no longer resolves. **Fix.** Refuse delegated tokens on GET /v1/oauth/consents and DELETE /v1/oauth/consents/{id} exactly as POST /v1/oauth/consent already does (404, the same wording used elsewhere for a caller who is 'looking at a path that does not exist'), optionally allowing a delegation to end only the one connection its own `del` claim names. Add a case beside T41 asserting that a delegated token gets 404 on both routes and that it cannot revoke a connection other than (optionally) its own.

### A Postgres restore rolls groups_version back, so the version-keyed principals cache in Redis can serve group memberships from the discarded timeline

<a id="core-authz-cache-ts-principalscachekey-groups-version-rollback-on-restore"></a>fingerprint `core/authz/cache.ts:principalsCacheKey:groups_version-rollback-on-restore`

The effective-principals cache stores a principal's transitive group set (the user plus every group it belongs to) in Redis under acl:principals:{org}:{type}:{id}:v{groups_version}. On a hit it returns that set without any other check. Its design says staleness is impossible because a membership change bumps organizations.groups_version, so every later read builds a different key. That only holds while the version never goes down. A pg_restore puts groups_version back to the value in the dump. Redis is not part of the restore. The Compose profile persists it on a named volume (--save 60 1), the runbook stops only worker, api and mcp, and nothing in the repository deletes or namespaces acl:principals:* keys. So the first trigger-driven change after the restore (any group, group_members or grants write) moves the version onto a number the discarded timeline already used. If an entry for that version is still within NACRE_ACL_CACHE_TTL (default 60 s, max 3600 s), a principal gets the cached memberships from before the restore. Grants are reloaded from the database, but a cached group that the restored database says the user is not in still contributes that group's grants. Example: a user added to a group after the snapshot (for instance an intruder adding themselves, which is a reason to restore) keeps that group's layers until the entry expires. The hunter reproduced this locally against real Postgres with the real trigger, modelling the restore by writing the snapshot rows back with triggers off. Whether it happens in a real deployment depends on how long passes between the last pre-restore cache write and the first post-restore request, which source cannot settle.

**Blockers:**
- Whether a post-restore request can arrive within NACRE_ACL_CACHE_TTL of a pre-restore cache write for the same re-used version depends on the deployment's TTL and restore procedure. With the 60 s default and the runbook's manual stop, restore and rebuild it is unlikely. It is plausible with a raised TTL, or with a restore onto a running installation such as the commercial backup module's screen restore, whose code is not in this repository.
- Whether the deployment's Redis survives the Postgres restore unflushed is not visible in source: an operator procedure or a module-side step may flush it. The shipped Compose file does persist it.
- The local reproduction (agents/h14-collections/artifacts/result.txt) modelled pg_restore by writing the snapshot rows back with triggers disabled, and drove cachedEffectivePrincipals plus resolve directly rather than the HTTP API. It did not run pg_dump/pg_restore or a real Redis through the API path.

### Model-endpoint responses (embedder, reranker) are buffered with no per-response byte cap, so a tenant-steered embedding endpoint can exhaust the shared worker's heap

<a id="model-endpoint-response-body-no-byte-cap"></a>fingerprint `model-endpoint-response-body-no-byte-cap`

Every model-endpoint response is read with `await response.json()`. There is no application byte limit, and the undici Agent in egress-fetch.ts sets no `maxResponseSize`. The only bound is the request timeout: 120 s for the worker, 15 s for the API embedder and 3 s for the reranker. The embedding endpoint can be steered by a tenant. An org_admin stores any public http(s) `endpoint` through POST /v1/embedding-providers. admitEmbeddingEndpoint (adapters.ts:2348) refuses only private and internal addresses, and NACRE_EMBED_TENANT_PROVIDERS defaults to true (config.ts:1144). When the worker embeds that tenant's documents, sendBatch buffers and JSON-parses the whole response. Local measurement through the real egressFetch transport: a 40 MiB response made of a JSON array of zeros became 20,971,521 elements, 213 MiB of heap and about 521 MiB RSS, where the legitimate answer for one input is a few KB. With the heap capped at 96 MiB, the same body killed the process with `FATAL ERROR: Reached heap limit … JavaScript heap out of memory` (exit 134). That kill is a V8 abort that no try/catch handles, not a caught error. The worker is one serial loop (`while (running)`, main.ts:838) that claims documents across every organization. An OOM kill therefore stops ingestion for every tenant on that replica until it restarts. The claimed document is then reclaimed after NACRE_INDEX_LEASE (900 s by default). Correction to the hunter's wording: this is not an unbounded crash-loop. The claim UPDATE increments `attempts` (claim.ts:118), and reapOnce marks a document failed once `attempts >= NACRE_INDEX_MAX_ATTEMPTS` (reap.ts:63, default 5). Each attacker document can therefore cost at most about five worker kills. A sustained effect needs the attacker to keep ingesting new documents. The same unbounded read exists in the multi-tenant API process (HttpEmbedder.send adapters.ts:1156, used for query embedding) and in HttpReranker.rank (rerank.ts:100). The reranker endpoint is configured by the operator, so it is a lower-severity instance. endpointReason (endpoint.ts:120) also calls response.json() without a bound on the error path.

**Blockers:**
- The deployed worker and API container memory limits, and the resulting V8 heap size, are not in the repository. They decide how large a body, delivered within the 120 s worker window, the attacker needs before the process is killed. Locally the heap amplification is about 5x the body for a numeric JSON array.
- Cross-tenant impact requires a multi-tenant installation (several organizations, for example with the enterprise tenancy module) in which org_admins are not the operator, with NACRE_EMBED_TENANT_PROVIDERS=true, which is the default. On a single-organization open-core install the org_admin is the operator and the effect is self-inflicted.
- Recovery depends on the supervisor and the replica count, which are deployment facts: how fast a killed worker restarts, and whether other worker replicas keep claiming other tenants' documents. Source bounds each malicious document to NACRE_INDEX_MAX_ATTEMPTS claims (default 5), each separated by NACRE_INDEX_LEASE (default 900 s). Whether per-tenant document quotas or ingest rate limits bound the number of such documents depends on the deployment.

**Local next step.** Already observed: through the real egressFetch transport, a 40 MiB numeric JSON body becomes about 213 MiB of heap and kills a process capped at a 96 MiB heap with a fatal, uncatchable OOM (agents/v07/artifacts/result.txt). To finish the local half, run the real worker loop in the sandbox with --postgres. Seed two organizations, give org A a layer whose provider endpoint is a trusted loopback origin serving the large body, and give org B an ordinary document. Run the worker with NODE_OPTIONS=--max-old-space-size set small. Observe that the worker dies on A's document, that B's document stays pending until restart, and that A's document increments `attempts` per claim and ends failed after NACRE_INDEX_MAX_ATTEMPTS (use a small NACRE_INDEX_LEASE, minimum 60). Keep bodies at 64 MiB or less, within the sandbox limits.

**Owner-observed check.** An operator, on a non-production multi-tenant stand with NACRE_EMBED_TENANT_PROVIDERS=true: as a test tenant's org_admin, create an embedding provider pointing at an operator-controlled public test server that answers /embeddings with a JSON array streamed to roughly (worker heap / 4) bytes. ### Parser URL guard accepts NAT64-embedded private/link-local addresses that the core egress guard decodes and refuses

## 4. Rejected candidates (informational, not findings)

Two hunter-proposed candidates were independently re-examined by a fresh verifier and found not to hold up; recorded here only because they explain why the corresponding coverage units show no finding, never as issues to act on.

- **`nacre/api/ingest-queue-holds-pool-connection-across-object-store`** — Ingest holds a pooled DB transaction across the object-store PUT, and the pool has no acquisition timeout. Rejected under the candidate gate: 'do not strengthen ordinary work into shared availability.' (1) The starvation needs object-store latency or retryable errors. Those are a fault in an operator-run dependency that no tenant principal can trigger: an object-store 5xx, 429 or transport failure is not tenant-controlled. (2) What a writer can control is ordinary work. Bytes are buffered before queue() runs, so the connection is held only for the server-to-store PUT of at most 50 MB. Ingest is rate-limited per organization (600/hour by default) and per principal through admitRequest. Holding a connection takes roughly as much upload work as it denies, so there is no meaningful amplification. (3) The pool recovers by itself: a waiter is served once the PUT returns, and there is no nested acquisition or deadlock on this path in the open core. (4) The hunter's local result (agents/h19-pool/artifacts/result2.txt) used a pool of max=1 with a stub put that blocked on a latch indefinitely. It shows only that pg queues a waiter behind a held connection, which is true of every pool. It does not show that a lower-trust principal can produce sustained saturation at real pool sizes. The module-gate nested-acquisition concern depends on enterprise code outside this repository. What is left is hardening: move the PUT ahead of the transaction, which the code's own comment about stray objects already allows, set a pool acquisition timeout that answers 503, and add a per-attempt timeout on the S3 fetch, which has none today. None of these is a finding with an affected principal or resource.

- **`packages/api/src/adapters.ts:document-grant-survives-delete-and-reattaches-on-resurrection`** — A document-scoped grant on a deleted document re-attaches to content later sent under the same external_id. The source does not show an unauthorized disclosure. (1) The documented identity model makes (layer, external_id) the document: a re-send replaces that document and keeps its document_id (docs/api.md:457), and reviving a deleted row under its id is a documented, deliberate behaviour (docs/upgrading.md:1204-1209). (2) The same effect happens with no delete at all. A writer who sends new content under an existing external_id overwrites the content of a document that already carries the grantee's allow, and the grantee reads it. That is how a document-scoped grant is meant to work (access to that document as it changes), so the delete step adds no new boundary. (3) The grantee gains no access beyond a grant an administrator explicitly issued on that document identity. The grant stays visible in GET /v1/grants and can be revoked through DELETE /v1/grants/{id} at any time, and the plan is computed per request, so revocation takes effect immediately. (4) While the document is deleted, every grant is refused (store.ts:87-89, resolve.ts:138-141), so invariant I5 holds. Denies survive the same way, which fails in the safe direction. (5) Only the commercial acl-advanced module issues document-scoped allows; the core issues none. What remains is a hardening note: deleting a document could remove or reset the document-scoped grants that name it, as layer deletion does, so that reusing an external_id after a delete starts from no document-level access. The local Postgres run was not performed, because the mechanism is not in dispute and the outcome depends on the documented design rather than on an unobserved fact.

## 5. Hardening notes and positive patterns

These are not findings: no record below crosses a trust boundary on its own, and none has severity. They are concrete, source-grounded observations surfaced by hunters while covering their assigned units, kept here so an owner can decide whether to act on them. Grouped by theme.

**Session and credential lifetime**
- Enrolling an *additional* second factor (`POST /v1/me/second-factor`) needs only a valid session — no fresh re-authentication and no proof of an existing factor — so a stolen session can silently add an attacker-controlled authenticator that later satisfies a require-2FA policy. Removal already requires a current code; consider requiring one for addition too.
- The enrolment challenge JWT (900s TTL) is a bearer token, not stored server-side and not single-use, so an intercepted challenge can be replayed to enrol more than one factor within its lifetime. The WebAuthn and recovery challenges are already spent on use; this one could be too.
- A demoted or disabled `org_admin`'s already-issued access token keeps the `org_admin` role for the rest of its TTL (claim-derived, no DB re-check), during which it can mint a persistent service account and grant. The window is documented; re-reading `users.role`/`disabled_at` on credential-minting writes specifically would remove it.
- STDIO authenticates once at connection time and never re-checks `service_accounts.revoked_at`; a revoked key does not end a running STDIO session. Low real-world impact (the process already holds direct DB credentials), but it is the same root cause as the confirmed OAuth-refresh finding.

**Cross-tenant and RLS depth**
- `nacre_app` inherits `nacre_worker` (BYPASSRLS) by default (migration 0008), so a SQL-injection-class bug in the API process is not actually stopped by row-level security as a second line — the API connection can `SET LOCAL ROLE nacre_worker` and read any tenant. A separate, non-inheriting login role for the worker would restore RLS as real defense in depth.
- A restored PostgreSQL snapshot can move `organizations.groups_version` backwards while Redis's `acl:principals:*` cache entries survive up to `NACRE_ACL_CACHE_TTL`; a membership the restore undid can be served from cache for up to that window. The restore runbook does not mention flushing Redis.
- `/metrics` (open unless `NACRE_METRICS_TOKEN` is set) labels series with every tenant's organization slug, read through `acrossOrganizations`. On a reachable multi-tenant installation this lets anyone enumerate tenant slugs and per-tenant document counts.
- The restore runbook does not warn that a restore silently undoes every revocation made after the snapshot (rotated refresh-token families, revoked service-account keys, withdrawn consents, disabled users); access can briefly outlive its documented revocation.

**Resource exhaustion at the edges**
- The embedder and reranker HTTP clients (worker, API embed path, `rerank.ts`) call `await response.json()` with no byte cap on vendor responses before extracting the needed fields; a misbehaving or compromised endpoint could force large in-memory buffering. A shared bounded-read helper across all three call sites would close this once.
- The Python embedding adapter reads the whole `Content-Length` body before any size check, runs an unbounded `ThreadingHTTPServer`, and is unauthenticated on its own network; Helm's NetworkPolicy restricting it to api/mcp/worker is off by default.
- `claimNext` is one cross-organization FIFO queue with strictly serial workers and no per-tenant fairness — one organization's backlog can delay every other organization's ingest for its duration.
- The parser sidecar holds a worker slot for as long as `pdf_inspector`/`anydoc` take, with no deadline of its own; the worker's 120s abort does not cancel the sidecar thread.

**Small authorization edges worth tightening**
- `PostgresGrants.issue`'s `ON CONFLICT ... DO UPDATE SET effect = 'allow'` silently turns an existing module-issued **deny** into an **allow** on re-issue of the same (principal, scope, permission). A scope admin can already revoke that deny by deleting it, so this is not new authority today, but a core that refuses to *issue* denies should refuse the upsert too (`DO NOTHING` when the existing row is a deny) rather than overwrite it.
- Layer `document_count`/`failed_count` count every live document in the layer, not just the ones visible under document-level denies a commercial module might apply (the code comment already acknowledges this).
- `GET /v1/layers/{id}/reindex` is reachable at plain `read` but returns `check.unresolved` entries containing external ids that `PostgresReferenceQueries` otherwise restricts to `admin`.
- A metadata or filter key of exactly `__proto__` passes the key-shape regex and the assignment sets the object's prototype rather than a property, silently dropping that key from filters and stored ingest metadata rather than being stored or refused. Not a widening of access, but inconsistent with the module's own "refuse, don't drop" rule; building the object with `Object.create(null)` would close it.
- A presigned `source_url` is bound to the object *key*, and re-ingest overwrites that key in place — so within `NACRE_PRESIGN_TTL`, a link minted before a revocation can return content written *after* it. Binding to an object version would tie the link to the bytes the read check actually covered.

**Process and supply chain**
- Compose connects to PostgreSQL as a superuser, so forced row-level security has no effect in the default local developer setup (this is documented behavior for development, not production).
- The CLA GitHub Actions check runs a script taken from the pull request itself.
- Base images and pip wheels are not pinned by hash.
- `uploadDescriptor` interpolates a base URL into a single-quoted curl line with no shell escaping; safe with the shipped `NACRE_CANONICAL_URL`/MCP-base wiring, but an embedder relying on the `Host`-header fallback could emit an injectable command line.

Sixty more granular observations of this kind were recorded by individual hunters against their assigned coverage units and are preserved in the run's internal working files; the selection above groups the ones with the clearest cross-cutting value. None changes the confirmed-findings count or any severity above.
